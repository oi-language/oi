# Oi 0.0.2 语言升级设计

日期：2026-08-16
状态：已确认

## 1. 目标

新增完整、不可变的 Oi `0.0.2` 语言快照，并以插件包装版本 `0.0.3` 交付。此次升级以真实 Oi Skill 的设计和执行证据为依据，同时解决两类问题：

1. 生产级 Skill 缺少 keyed collection、显式逐项决策和可扩展的数据处理结构，导致大量 slice 线性查找、嵌套循环、重复 helper 和过大的 semantic aggregate。
2. Agent 加载大 source graph、host-invoke 入口和证明 typed Reply landing 的流程过于人工，曾出现读取截断、上下文污染、手写 Pass payload 和没有实际调用入口却声明成功的问题。

成功标准是让大型 Oi Skill 的数据流更短、更显式，让每次执行都具备封闭输入、精确源码身份、typed journal、具体 Reply 和可重放 receipt。Oi 仍是由 Agent 直接执行的独立语言，不生成执行包，不引入 VM、binary 或第二运行时。

## 2. 证据范围

本设计提炼三个真实工作流的可观察结论，不复制外部 Skill 正文，也不修改外部仓库：

- Go import alias Skill 的 Oi runtime 设计与实现。
- manage-project Skill 的 Oi runtime 设计与实现。
- 在 25 个 Go repositories 上实际使用 Oi Skill。

两个外部 runtime 合计约 6,166 行、272,498 字符；仓库内 bundled toolchain 也存在 2,774 行的单个 compiler source。实际运行记录证明：问题既不只是 Skill policy，也不只是语法缺糖。缺少 keyed collections 和受限 judgment 使行为难以审查；无清单加载、无 sealed root context 和无标准 receipt 使“是否真正执行”难以证明。

非 Git 多仓 bootstrap 和错误 alias 推荐本身属于领域 Skill 行为，不进入语言核心。0.0.2 只提供足以安全表达、隔离和验证这些工作流的通用构造。

## 3. 已选方案

采用“证据驱动的 breaking snapshot”：

- 增加 deterministic map、set 和 indexed/keyed iteration。
- 把 context-sensitive judgment 与 deterministic aggregate derivation 分开。
- 使用显式 source manifest、逻辑分块读取和源码预算。
- 根入口与 child task 一样使用 sealed context。
- 每次真实调用产生语言定义的 typed execution receipt，并由 debugger/replay 验证。
- 保留 tasks、channels、detach、handoff 和 durability；三个会话没有证明这些按需 runtime shards 是问题来源。

不采用以下方案：

- 只增加 collection 和 receipt、保留 unrestricted aggregate semantic expression：无法阻止一次方括号表达式生成整张决策表。
- 删除并发与 durable runtime、把 Oi 重置为顺序语言：会丢失已发布能力，但不能直接解决 source loading 或执行证明。
- 生成 Markdown、JSON 或 binary execution capsule：会引入新的行为真源和执行层，破坏 Agent 直接执行 `.oi` 的产品边界。

0.0.2 不要求 0.0.1 源码零修改升级。兼容性由 `upgrade-oi` 显式检查和报告，而不是由新 snapshot 静默重解释旧源码。

## 4. 版本与仓库架构

### 4.1 语言与包装版本

- `plugins/oi/skills/using-oi/versions/0.0.1/` byte-for-byte 保持不变。
- 新语言真源位于 `plugins/oi/skills/using-oi/versions/0.0.2/`。
- `0.0.2/execution.md` 是 0.0.2 唯一基础语言文件和 manifest。
- `0.0.2/runtime/` 只描述 core-declared constructs 的详细 dynamics。
- `0.0.2/std/` 和 reachable `.oi` 承载可执行行为。
- 三端 marketplace 与 plugin manifests 同步提升到包装版本 `0.0.3`，同时交付语言快照 `0.0.1` 和 `0.0.2`。
- `oi.mod` 始终是语言版本的唯一选择来源；包装版本不得被当作语言版本。

### 4.2 直接执行边界

Agent 继续直接加载、验证和执行 `.oi`：

- `compile-oi` 只验证，不生成执行产物。
- 不新增 VM、interpreter binary、script runtime 或 generated capsule。
- `using-oi/SKILL.md` 只触发、解析版本、加载、绑定、映射和路由入口。
- sealed context、source loading、operation identity、journal 和 receipt 的行为属于 versioned specification，不由 adapter prose 私自定义。

### 4.3 跨版本工具

bundled toolchain 自身迁移到 `oi 0.0.2`。它必须继续识别已安装的 `0.0.1`：

- 对 0.0.1 target 使用 0.0.1 的 grammar、loading 和 diagnostics。
- 对 0.0.2 target 使用 0.0.2 的 source manifest、budgets、collections、derivation、sealed context 和 receipt。
- 不用 0.0.2 formatter 或 compiler 规则重新解释 0.0.1。

## 5. Deterministic collections

### 5.1 类型与字面量

0.0.2 新增：

```oi
map[K]V
set[T]
```

示例：

```oi
var owners map[text]Owner = map[text]Owner{}
var touched set[fs.Path] = set[fs.Path]{request.Root}
```

map key 和 set element 必须具有 canonical total order：

- `bool`：`false` 先于 `true`；
- `int`：数学升序；
- `text`：unsigned UTF-8 byte order；
- enum：声明顺序；
- 以上类型的 named type：使用其底层 canonical order，但保持类型区别。

struct、slice、map、set、optional、failure 和 runtime handles 不能作为 key/element。map value 遵守普通值和 runtime-handle scope 规则。map/set 在其 key、element 和 value 都 durable 时递归 durable。

map/set 是有限值，零值为空集合，复制不产生共享可变状态。它们不可比较。`len` 返回元素数量。

### 5.2 操作

新增内建调用：

- `has(mapping, key)` 与 `has(set, value)` 返回 `bool`。
- `put(mapping, key, value)` 返回插入或替换后的新 map。
- `add(set, value)` 返回包含该值的新 set；已存在时结果不变。
- `remove(mapping, key)` 与 `remove(set, value)` 返回删除后的新值；目标不存在时结果不变。
- `mapping[key]` 返回 `V`；key 不存在时在索引位置产生 runtime `MISSING_KEY`。

map literal 中后出现的重复 key、set literal 中重复 element 在后一个元素位置产生 `DUPLICATE_KEY`，不采用 last-write-wins。

### 5.3 迭代

0.0.2 支持：

```oi
for index, value in values {
    // slice index ascending from zero
}

for key, value in mapping {
    // canonical key order
}

for value in members {
    // canonical set element order
}
```

原有 `for value in slice` 保留。每个 `for ... in ...` 在进入时取得不可变 iteration snapshot；循环体重新绑定原集合不会改变当前遍历的数量、顺序或值。

## 6. Judgment 与 derivation

### 6.1 Bounded judgment

普通 `[...]` 继续表示一次 contextually typed Agent judgment 或 predicate。生成结果必须是 bounded judgment value：

- primitive、enum、以上值的 named type；
- optional bounded value；
- 字段递归满足本规则的固定 struct。

结果类型递归包含 slice、map 或 set 时，在 `[` 产生 static `UNBOUNDED_SEMANTIC_RESULT`。judgment 不能通过 text 私有协议规避该限制；内部集合、状态和 diagnostics 必须保持 typed。

judgment 的动态输入只能来自显式 interpolation。它不能观察父会话、隐藏 memory、未映射工具输出或未作为参数传入的项目事实。结果不唯一时保持 `AMBIGUOUS_SEMANTIC_VALUE` 或 `AMBIGUOUS_SEMANTIC_MATCH`。

### 6.2 Aggregate derivation

新增 `derive` 前缀：

```oi
var inventory Inventory = derive [decode and normalize {source}]
```

`derive [...]` 表示完全由显式输入和已加载 snapshot 决定的结构转换：

- 可返回 handle-free struct、slice、map、set、optional 或 named value。
- 必须具有显式 target type，不能由 `:=` 无上下文推断。
- 可以表达 parse、decode、normalize、group、sort、canonical render 和其他唯一的数据变换。
- 不得执行 context-sensitive policy choice，不得读取会话或外部状态。
- 不能隐藏 effect、循环控制、retry、dispatch、handoff 或 stop。
- 无唯一结果时在 `derive` 产生 runtime `NONDETERMINISTIC_DERIVATION`。

一项工作若需要对 300 个候选作判断，Oi 必须显式遍历 300 个候选、为每个候选取得一个 bounded judgment，再用 map/set/slice 显式聚合。question 数量、decision identity 和证据边界因此可观察。

contract 和 `~=` 仍使用单次 `[...]` predicate。它们不取得 aggregate generation 权限。

## 7. Source manifest 与解析

### 7.1 0.0.2 `oi.mod`

每个 0.0.2 module 必须声明完整 source inventory：

```text
module example
oi 0.0.2
source internal/model/model.oi
source internal/runtime/runtime.oi
source main.oi
```

规则：

- 恰有一个 canonical `module`、`oi` 和至少一个 `source` directive。
- `source` path 为 normalized module-relative UTF-8 path，不含反斜杠、`.`、`..`、空 segment 或 module escape。
- source directives 按 exact UTF-8 path bytes 严格升序且不重复。
- `main.oi` 必须存在并声明 package `main`。
- 非 main source 的 directory 最后一个 segment、文件 basename 和 package name 必须相同，例如 `internal/model/model.oi` 声明 package `model`。
- 每个 package directory 恰有一个 manifested source。
- import path 根据 module path 和 package directory 唯一解析到 manifest source。
- manifest 外的文件不属于程序，不参与正常执行扫描或加载。

0.0.1 modules 继续使用其已发布的 discovery semantics。

### 7.2 Logical snapshot read

spec、module metadata、target source、runtime shard 和 std source 的“读取一次”在 0.0.2 中表示一个 logical immutable snapshot：

- 宿主可用连续 chunks 读取物理文件。
- chunks 必须从 byte zero 单调推进到真实 EOF，无遗漏、重叠、回退或重复。
- logical close 记录完整 byte size、decoded character count 和 SHA-256。
- truncation marker、缺页、未到 EOF、无效 UTF-8 或读取期间 identity 变化都在解释源码前停止。
- runtime 只观察拼接和验证后的完整值；分页次数不是语言级多次读取。

### 7.3 Budgets

- 每个 0.0.2 project `.oi` source 最多 `16,000` decoded UTF-8 characters。
- 一个 target 的 reachable project source graph 最多 `128,000` decoded characters。
- product `.oi` 每行最多 `240` characters。
- versioned execution spec 最多 `14,000` characters。
- index prefix 最多 `2,500`，prefix+adapter 最多 `4,000`，adapter 最多 `1,500`。
- 每个 runtime shard 最多 `5,000` characters。
- runtime shards 和 standard packages 不计入 target project graph，但各自仍受对应文件预算和行预算。

collection 与 derivation 的详细 dynamics 进入 manifest-triggered runtime shards，不通过扩大 base-spec 预算实现。

### 7.4 Module diagnostics

0.0.2 至少定义以下 module/load diagnostics：

- `MISSING_SOURCE_MANIFEST`
- `SOURCE_MANIFEST_ORDER`
- `SOURCE_MANIFEST_PATH`
- `SOURCE_PACKAGE_DUPLICATE`
- `SOURCE_PACKAGE_MISMATCH`
- `SOURCE_IMPORT_UNDECLARED`
- `SOURCE_FILE_BUDGET`
- `SOURCE_GRAPH_BUDGET`
- `SOURCE_TRUNCATED`
- `SOURCE_CHANGED_DURING_LOAD`

所有 diagnostics 使用 phase、module-relative location、detail 和 trace 的既有 deterministic ordering 原则。

## 8. Sealed entry execution

### 8.1 Admission

0.0.2 phase order增加 `execution admission`：

```text
parse → module → type → effect mapping → input binding → execution admission → runtime
```

host invocation 只有在宿主能建立 sealed entry context 时才能通过 admission。该上下文只包含：

- 已验证的 execution spec、target sources、runtime shards 和 standard packages；
- 按 entry declaration 顺序绑定的 typed caller inputs；
- exact effect mappings、authorities 和 runtime policy；
- 当前 activation 的 trace、checkpoints 和 journal。

它排除 parent conversation、历史回复、verification 文档、测试 expected values、Agent memory、局部工具输出和未映射能力。宿主无法提供隔离时，在 entry 开始前产生 `CONTEXT_ISOLATION_UNAVAILABLE`，target main invocation count 保持 zero。

### 8.2 Effect attempts 与 completion

- required effect signature、authorities 和 mapping 在入口前验证。
- direct captured effect 保留已发布的 optional boundary 原则。
- 宿主为兼容性进行的 probe 或失败尝试记录为 mapping attempt，不计为 target effect operation。
- target effect 只有在完整 typed result 通过边界后才记录 Completed。
- Started 但没有可信 completion 的 external effect 进入 indeterminate 状态，不猜测、重试或伪造结果。
- semantic judgment、derive、collection iteration、effect、task launch、await、channel commit、detach 和 handoff 都取得稳定 operation identity。

## 9. Execution receipt 与 replay

### 9.1 Receipt 边界

每次已识别为 0.0.2 snapshot 的 invocation 都返回语言定义的 `ExecutionReceipt` sidecar。它不是 target value、effect payload、source file 或 generated artifact：

- target program 不能读取 receipt。
- receipt 默认只存在于调用结果中，不写入项目。
- concrete typed Reply payload 原样交给 caller，receipt 单独交付。
- entry 前失败仍产生 terminal receipt；无法解析或安装 snapshot 的 bootstrap failure 仍使用 bootstrap diagnostic。

### 9.2 Receipt 内容

receipt 至少包含：

- language snapshot、module、entry 和 ordered manifest closure；
- 每个 loaded artifact 的 normalized path、byte size、decoded characters 和 SHA-256；
- caller inputs、effect mappings、authorities 和 runtime policy 的类型身份与 canonical digest；
- ordered operation ID、kind、source location、Started/Completed/Failed/Indeterminate 状态；
- semantic、derive、collection iteration、effect 和 task result 的 type identity 与 digest；
- reply effect identity、operation ID、payload type 和 payload digest；
- terminal completion、failure 和实际预算使用量。

receipt 不暴露 secret input、effect result、stdout、stderr 或 user answer bytes。完整 typed values 只存在于受保护的 execution journal；receipt 记录其 canonical digest。

### 9.3 Replay

`debug-oi` 使用 typed bindings、execution journal、receipt 和 typed effect transcript 执行只读验证：

- 不调用 target entry 或 target effects。
- 重新验证 source identities、manifest closure、phase order、operation order、reply landing、failure 和 terminal state。
- source、bindings、mapping、authority、journal、transcript 或 receipt mismatch 都 fail closed。
- replay 不能把源码计数、authority grep、手写 JSON/Markdown payload 或先前文档中的期望结果当作 execution evidence。

receipt 与 replay 为 conforming host 提供可审计证据，不声称对恶意伪造整个运行记录的宿主提供密码学远程证明。

## 10. Bundled toolchain

### 10.1 `using-oi`

- 精确解析 target `oi.mod` 并选择已安装 snapshot。
- 0.0.1 保留已发布加载语义。
- 0.0.2 执行 manifest load、logical snapshot reads、budget checks、sealed admission 和 receipt delivery。
- adapter 不复制 grammar、runtime algorithms 或 receipt construction。

### 10.2 `compile-oi`

- 自身运行于 0.0.2。
- 根据 target snapshot 验证 0.0.1 或 0.0.2。
- 0.0.2 report 包含 source manifest、graph budget、authorities、shards 和 exact diagnostics。
- 静态拒绝 unbounded judgment，并验证 map/set/derive typing。

### 10.3 `format-oi`

- 根据 target snapshot 选择 formatter grammar。
- canonicalize 0.0.2 map/set literals、derive 和新 for bindings。
- 不跨 snapshot 改写 source。

### 10.4 `debug-oi`

- entry 接受 typed bindings、journal、receipt 和 typed transcript。
- 不执行 target main 或 effects。
- 输出 replay validity、ordered events、required transcript entries 和 diagnostics。

### 10.5 `bench-oi`

- 每个 target 在 sealed fresh context 中执行。
- 同时核对 concrete typed Reply 与 matching receipt。
- required/forbidden observations 包含 context visibility、effect counts、reply landing 和 budgets。

### 10.6 `convert-oi`

- 增加显式 target snapshot input。
- 生成 0.0.2 module 时同时生成 canonical `oi.mod` source manifest。
- Preview 零写；Apply 保持 guarded writes 和非原子多文件 publish 的诚实报告。

### 10.7 `upgrade-oi`

- 明确支持只读分析 `0.0.1 → 0.0.2`。
- 报告缺失 source manifest、单文件/graph 超预算、aggregate semantic expressions、需要 `derive` 的 deterministic transforms、collection migration opportunities 和 sealed-host requirements。
- 可以把确定的 metadata 或表面语法变化标记为 automatic，但不写文件。
- package split、judgment decomposition 和领域 policy 变化标记为 manual。
- 不把 target availability、packaging version 或一次 target compile success误报为完整源码兼容。

## 11. Corpus 与派生案例

### 11.1 Core corpus

0.0.2 corpus 至少覆盖：

- map/set literal、duplicate、lookup、put/add/remove、len 和 canonical iteration；
- slice indexed iteration 和 iteration snapshot；
- 合法 bounded judgment；
- aggregate judgment 的 `UNBOUNDED_SEMANTIC_RESULT`；
- 合法 aggregate `derive` 与 `NONDETERMINISTIC_DERIVATION`；
- source manifest 缺失、排序、path、package 和 import diagnostics；
- logical chunk success、truncation、source drift 和 budget failures；
- sealed context admission success/failure；
- completed、failed 和 indeterminate effect；
- receipt/replay success 以及每类 identity mismatch。

每项新增语义先有 corpus observation，再修改规范或工具实现。

### 11.2 会话派生案例

在 `docs/language/cases/0.0.2/` 新增三个小型、通用案例：

1. `registry-analysis`：使用 map/set、per-item judgment 和显式聚合；forbidden observation 是一个 semantic expression 生成整张决策表。
2. `multi-root-bootstrap`：从非 Git semantic root 通过 typed observations 建立有界成员集合；不引入 Git/Go 专用核心构造。
3. `actual-invocation-proof`：parent context 预置 expected answer，sealed target 必须不可见；只有 real entry invocation、typed Reply 和 matching receipt 通过。

案例只复现 required/forbidden observations，不读取或复制 subpowers 源码、spec 或 verification 文档。

- `docs/language/` 明确区分 normative 0.0.2 specification、0.0.1 历史 rationale、toolchain contracts 和派生案例。

## 13. Release gates

只有以下条件全部满足，才发布 language `0.0.2` / packaging `0.0.3`：

1. `using-oi/versions/0.0.1/` 与发布基线 byte-for-byte 相同。
2. 新 toolchain 对完整 0.0.1 corpus 产生相同 observations。
3. 0.0.2 corpus、三个派生案例和 cross-tool scenario 全部通过。
4. bundled toolchain、stdlib、adapters、examples、corpus 和 version pins 作为一个 language release unit 迁移完成。
5. 所有 product `.oi` 满足 240-character line limit、16,000-character source limit 和 128,000-character reachable target graph limit。
6. execution spec、prefix、adapter、prefix+adapter 和 runtime shards 满足既有字符预算。
7. compile、format、debug、bench、convert、upgrade 对各自有效、无效和失败案例返回 concrete typed Reply 与 matching receipt。
8. 三端 marketplace 与 plugin manifests 都是包装版本 `0.0.3`，且没有把该值写入 `oi.mod` 或 installed snapshot list。
9. README、toolchain docs、language rationale、corpus docs 和 examples 描述同一 released behavior。
10. 仓库没有新增 Python、JavaScript、TypeScript、Shell、PowerShell、batch、binary、VM 或 executable test helper。
11. UTF-8/LF、manifest closure、diagnostic ordering、character budgets、`git diff --check` 和最终 Git diff 全部通过。

任一 gate 失败时继续迭代，不发布部分 snapshot，不修改旧 snapshot 来规避失败。

## 14. 非目标

- 不修改、迁移或发布 subpowers。
- 不保证任何领域 alias、owner、project layout 或其他 Agent judgment 必然正确。
- 不把 Git、Go、registry 或多仓 bootstrap 变成语言 built-in。
- 不增加 package manager、binary compiler、VM、ambient memory、hidden retry 或隐式 authority widening。
- 不生成 Markdown/JSON execution capsule。
- 不为 0.0.1 源码提供隐藏 compatibility mode。

## 15. 风险与控制

- **Manifest 维护成本**：source inventory 是显式模块接口；compiler 检查排序和 package/path/import closure，避免运行时扫描猜测。
- **Source budget 迫使拆包**：这是有意的 Agent-context 边界。`upgrade-oi` 精确报告超限文件和 manual split，不自动切割语义。
- **`derive` 被滥用为 judgment**：规范限制其只依赖显式输入且必须唯一；corpus 和真实案例检查 policy choice 不得进入 derive。
- **Bounded judgment 仍可用 text 私有编码绕过**：language discipline 禁止把内部集合、状态或 diagnostics 编码为 text protocol；toolchain和 review gate 扫描已知违规形态。
- **Sealed context 在部分宿主不可用**：0.0.2 fail closed，不回退到 ambient execution。0.0.1 仍可按其旧 snapshot 运行。
- **Receipt 被误当作密码学证明**：文档只声明 deterministic auditability；matching replay 能发现 accidental、incomplete 和 mismatched evidence，不能证明恶意宿主诚实。
- **跨版本工具复杂度**：target snapshot 决定 parser/formatter/runtime contract；测试矩阵要求 0.0.1 observations 不漂移。
- **Spec 膨胀**：collections、derivation 和 receipt detailed dynamics 使用按需 shards，base file 和 adapter budgets不提高。

## 16. 实施顺序
